# WinZip AES ZIP implementation plan

> Use superpowers:executing-plans to implement each tested checkpoint.

Goal: authenticated single-volume ZIP32 Store/Deflate reading, testing and AES-256 creation, through existing native password and archive workflows.

Architecture: system libarchive's mature WinZip AES codec, backed by platform crypto, remains the reader/writer. Extend the conservative ZIP envelope validator specifically for AES; ordinary ZIP editing keeps its original admission rules. After complete password/authentication/decompression verification, retain a private plaintext TAR in the existing snapshot-owned spool lifecycle. No password is retained by snapshots. Creation configures `zip:encryption=aes256`, verifies the completed archive, and uses existing exclusive publication.

Alternatives considered: importing 7-Zip's WzAes codec would provide a pinned crypto implementation but requires another ZIP transform layer; implementing CTR/HMAC directly would add unnecessary security-sensitive code. Use libarchive only if independent tamper/interoperability tests pass on both macOS runners. Unsupported crypto capability fails closed, never ZipCrypto fallback.

Constraints: macOS 13+, arm64/Universal, no external executable/runtime dependency, no encrypted editing, no multipart/ZIP64/ZIPX, no unrelated UI/format changes. Passwords are synchronous operation-local arguments, not logs/URLs/preferences. Existing ZIP defaults and presets remain unchanged.

Review focus: empty encrypted payload authentication; AE-1 versus AE-2 CRCs; central/local/descriptor consistency; authenticated invalid Deflate; partial-output cleanup on authentication failure. Existing system writer leaves zero-length files/directories plaintext, with honest metadata; test externally encrypted empty files separately.
